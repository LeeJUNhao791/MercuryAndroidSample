# Tech Spec 技术方案评审

## 使用场景
产品或技术方案文档（PRD、技术设计文档、API 规范）写完之后，在正式编码前运行此 Prompt 进行评审。

**触发词**：评审技术方案、技术评审、方案评审、Spec 评审

## 输入参数
- `$SPEC_CONTENT`：技术方案 / Tech Spec 的完整内容（可以粘贴文档或描述）

## Prompt 正文

---

你是大厂 Android 技术负责人，带过 10 人以上团队。请严格评审以下 **Tech Spec / 技术方案文档**，从架构完整性、一致性和可实现性三个维度进行评审。

## Tech Spec 内容
$SPEC_CONTENT

## 评审维度

### 1. 一致性检查

| 检查项 | 预期 | 实际情况 | 问题 |
|---|---|---|---|
| 接口定义字段 ↔ 数据模型字段 | 字段名和类型完全对齐 | ? | ? |
| 状态机的每个状态 | 都有对应的 UI 描述 | ? | ? |
| 异常处理的每种错误 | 都有对应的错误码定义 | ? | ? |
| API 请求参数 ↔ 前端调用 | 完全匹配 | ? | ? |
| API 响应字段 ↔ 前端使用 | 完全匹配 | ? | ? |

### 2. 遗漏检查

请检查以下常见遗漏，每项给出发现的问题：

- **并发场景**：快速点击、页面切换中的竞态条件是否有处理
- **数据一致性**：乐观更新失败后是否有回滚策略
- **生命周期**：configuration change（屏幕旋转）后状态是否恢复
- **权限处理**：运行时权限申请失败后的降级方案
- **网络状态**：无网络时的缓存策略和降级处理
- **边界数据**：空列表、超长列表、分页边界（第 0 页 / 最后一页）
- **错误恢复**：API 重试机制、重试次数限制、退避策略

### 3. 过度设计检查

| 检查项 | 问题 |
|---|---|
| 是否有为 MVP 阶段不需要的功能做的设计 | |
| 是否有可以用更简单方案替代的复杂设计 | |
| 是否引入了不必要的抽象层次 | |
| 是否引入了项目目前没有使用的中介技术（如 RxJava、Moshi 等） | |

### 4. 可实现性评估

| 模块 | 复杂度 | 预计工时 | 风险点 |
|---|---|---|---|
| 数据模型 | 低/中/高 | | |
| Repository / 数据层 | 低/中/高 | | |
| UseCase / 业务层 | 低/中/高 | | |
| ViewModel / 状态管理 | 低/中/高 | | |
| UI / Compose | 低/中/高 | | |

## 输出格式

### 问题汇总表

| 严重程度 | 模块 | 文件/接口 | 问题描述 | 修改建议 |
|---|---|---|---|---|
| 严重 | | | | |
| 一般 | | | | |
| 建议 | | | | |

严重程度定义：
- **严重**：会阻塞开发（P0）或导致线上 Bug（P1）
- **一般**：实现后发现需要返工的问题（P1/P2）
- **建议**：优化项，不影响功能（P2）

### 需要向产品确认的问题清单

列出 Spec 中没有定义清楚、必须向产品确认才能继续开发的问题。

### 通过评审的条件

以下全部满足时，Spec 可以进入开发阶段：
- [ ] 无 P0 级别遗漏
- [ ] 所有并发场景有明确处理策略
- [ ] 状态机覆盖所有业务流程
- [ ] API 定义和数据模型完全对齐
- [ ] 没有明显的过度设计

请逐项评审并给出最终结论。
